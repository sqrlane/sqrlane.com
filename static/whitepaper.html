Technical whitepaper · Working prototype

Trade-lane risk, decided.

Freight forwarders find out about disruption late, and then handle it by hand. Lanewatch closes the gap between knowing and doing — it watches the world for events that break trade lanes, works out which shipments are exposed, decides reroute or hold for each one, and drafts the emails a person would otherwise write. Every call keeps its reasoning.

In one paragraph

A disruption — a port strike, a river running low, a corridor closing — is known locally long before it is news globally. Lanewatch reads around twenty sources close to those events, decides which of your bookings are affected, and produces three things for each one: a decision, the reasoning behind it, and the carrier and customer emails it implies. Nothing is ever sent. A person approves, or does not. The whole loop runs on open-weight models that can be hosted inside the European Union, so the shipment data never has to leave.

The problem this addresses

A mid-size forwarder's operations desk does two jobs badly, through no fault of its own. It watches for disruption, which means someone reading trade press between other work. And it reacts to disruption, which means opening the booking system, checking which boxes are exposed, weighing the options, and writing the same six emails it wrote last time.

Existing risk platforms do the first job and stop. They raise an alert and leave the desk exactly where it was — knowing something is wrong, with all the work still to do. They are also priced for enterprise shippers, not for a forwarder with a few hundred bookings in the water.

The gap is not detection. It is everything after detection.

The part that makes it a loop

Risk platforms stop at stage 01. Execution tools start at stage 04 and assume someone already decided. Welding the two together — and writing down the reasoning in between — is the whole idea. A shipment rerouted on Tuesday is on the new route on Wednesday, and is no longer exposed to the thing that moved it. A shipment that is held accrues a day of delay for every day it waits, and carries that delay when it resumes. Holding is not free, and the system says so.

The line we hold

“The risk detection is real — it runs against live news right now. The shipments are synthetic, so I can show you a disruption on demand instead of waiting for one.”

Where the model decides, and where it must not

The most common way an AI logistics tool loses trust is by letting a language model do arithmetic. Lanewatch splits the work along a hard line.

Code computes the facts. Which chokepoints a route passes through. Which of them carry active risk. How many days an alternative adds. Whether that fits inside the schedule slack. What the revised arrival date is. All ordinary, testable code. Dates and sums never go near a model.

The model makes the call and explains it. Given those facts, is the right answer to move the box, hold it, or leave it alone — and why, in language an operations lead would accept.

This split has a useful side effect: a booking whose route carries no active risk never reaches the model at all. That is a genuine answer, not a shortcut, and it keeps a meaningful share of the board deterministic.

Guard rails around the model's answer

  • If the model proposes a route it was never offered, the reroute is refused and downgraded to a hold.
  • If it returns a decision value that isn't one of the three allowed, the result falls back to no-action.
  • If the provider fails entirely, transparent rules decide instead and every affected card is badged as rule-decided.
  • Each of those interventions is written into the shipment's reasoning record, so a refused answer is visible rather than silently swallowed.

Why there are no version numbers

This project has already been bitten once. A model name was hard-coded, the provider retired it, and the API answered with a 404 that is indistinguishable from a broken key — so every decision silently fell through to the rule-based fallback while the demo appeared to work. The system now asks the provider what it can run and picks from that list at start-up.

Treat the table above the same way: pick the class, verify the current best member of it at deployment time, and never pin a name you are not prepared to monitor. Any hard-coded model name is a scheduled outage.

Running it in Europe

Shipment data is commercially sensitive: lanes, volumes, customers, rates. The architecture is designed so none of it has to leave the EU.

Every model in the table above is open-weight, which means it can run on hardware you choose rather than being reached through someone else's API. That is the entire sovereignty argument — not a policy promise about where data is processed, but an architecture in which the question does not arise.

Lyceum Technology, a Berlin company, sells GPU capacity from data centres in Spain, Paris and the Nordics, with an OpenAI-compatible API. That compatibility matters more than it sounds: this prototype's provider layer is a single file, so moving from a US API to EU-hosted inference is a base-URL change rather than a rewrite.

Why scale-to-zero suits this workload exactly

Lanewatch is bursty by design. It is not a chat product with steady traffic; it does nothing at all until a disruption is detected or an operator asks, then makes a short burst of calls and goes quiet. Paying for an idle GPU around the clock would be the single largest waste in the system. An endpoint that shuts down between runs and bills per second matches the shape of the work.

A worked illustration, with the assumption stated plainly: an L40S at $1.19/hr is about $0.00033 per second. If a nine-call cycle occupies the GPU for twenty seconds, that cycle costs roughly $0.007. Ten disruptions a day across a year lands near $25 of inference.

Where that number is soft

The twenty seconds is an assumption, not a measurement — this prototype has not been benchmarked on that hardware. Real GPU time depends on model size, quantisation, batching and context length, and could plausibly be several times higher. The rate card is verifiable; the throughput is not, and anyone building a business case should measure it rather than trust the arithmetic above.

Built in Europe, for Europe

That phrase is doing a lot of marketing work across the sector at the moment, so it is worth being exact about what it means here and what it does not.

What it means concretely

  • The problem is European. The lanes, chokepoints and regulations modelled are the North Range ports, the Rhine, the Mediterranean corridors and EU customs entry — not a generic global abstraction with European labels applied.
  • The models can be European. Teuken-7B came out of a German research consortium and covers all twenty-four official EU languages; EuroLLM is an EU-funded project with the same coverage; Mistral is French. All are openly licensed.
  • The compute can be European. EU-domiciled GPU capacity in EU data centres, with no shared tenancy.
  • The data need never leave. Because the models are open-weight, shipment data is processed on infrastructure the operator controls. That is a property of the architecture, not a clause in a contract.
  • It suits the regulatory direction. Recorded reasoning for every decision, and a human approval gate before anything leaves the building, are exactly the properties an EU AI Act conversation asks about.

What it does not mean yet

The prototype as it stands calls a US inference provider. It was built against a free tier for speed of iteration. Everything above describes an architecture that supports EU-only operation, and a provider layer designed to make the switch cheap — but the switch has not been made, and no one should read the current deployment as sovereign. Saying otherwise would be exactly the kind of unbacked claim this project refuses to make everywhere else.

The pattern worth taking away

Every one of those was found by looking at real output, not by reasoning about the code. The rate limit in particular survived three rounds of confident wrong diagnosis until the fallback was made to state its own reason on screen. A system that degrades silently is worse than one that fails loudly, because you will demonstrate it in that state without knowing.

What this is not

Scope discipline is what kept this buildable. None of the following are in it, and none are accidental omissions.

  • Not route optimisation. Candidate routes are pre-defined. The system chooses among them and justifies the choice; it does not compute new ones.
  • Not a sending system. Emails, booking amendments, customs entries and TMS write-backs are all drafted and held. There is no transport layer in the codebase, and a test fails the build if one is ever imported.
  • Not integrated with any real TMS. The connector models the field mapping and describes the change a decision implies. It contacts nothing.
  • Not always-on. It runs on demand. For a demonstration, a button beats a background job.
  • Not measured. There are no accuracy figures, hit rates or time-saved claims anywhere in this document, because none have been measured. Inventing them is the fastest way to lose a room that knows the domain.

What production would require

The distance between this prototype and a product is not mostly model work. It is integration, trust and liability.

  • A real booking feed. One TMS integration, properly done, replaces the synthetic pool and is the single highest-value next step.
  • Inference moved in-region. Deploy the model classes above on EU capacity and benchmark them, replacing the illustrative costs here with measured ones.
  • Evaluation the domain would accept. A held-out set of historical disruptions, scored on whether the decision matches what the desk actually did — the only credible answer to “how good is it”.
  • Sending, deliberately and last. The approval gate exists because trust is earned in that order. Drafting well for months is the argument for eventually being allowed to send.
