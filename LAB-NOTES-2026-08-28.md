## 1. Where this started, and the problem underneath it

The day began with one question: **what is
[PriorLabs/TabPFN](https://github.com/PriorLabs/TabPFN), and can we use it to
test our models?**

TabPFN is a *tabular foundation model*: a transformer pre-trained on millions
of synthetic tables, so it learns a new dataset in a single forward pass — no
training loop, no hyperparameter tuning, sklearn-style `fit`/`predict`. Its
sweet spot is exactly the size of table a freight desk produces.

The honest answer to "can we test our models with it" was: **we had no models,
and worse, no ground truth to test anything against.** The decision layer is
an LLM with a rules fallback. Training or scoring any model on the rules
engine's own output would just relearn an if-statement and score a
meaningless 100% — and publishing that number would be the invented metric
this project refuses to produce.

So before TabPFN could be evaluated, the thing it would be evaluated *on* had
to exist. That shaped the whole day.

---

## 2. The hypotheses

Three, stated the way a lab notebook should state them — one we began with,
two that formed along the way. Each is falsifiable, and each got its verdict
the same day. (The verdicts are argued in full in sections 3 and 4; this is
the register.)

**H1 — the TabPFN hypothesis** *(stated at the start; tested in 4c).*
A pre-trained tabular foundation model, with zero tuning and a single fit,
matches or beats a tuned classical model (gradient boosting) at the desk's
three decisions — reroute/hold/do-nothing, delay, breach risk — when both
are scored against genuine ground truth. Its precondition is the reason the
practice world exists at all: with no ground truth, the hypothesis is not
testable, only fakeable.
**Verdict: supported, on all three tasks** — action 89.5% / 0.666 macro-F1
vs GBM's 88.1% / 0.608 (the edge concentrated on the rare classes, which
are the ones that matter), delay MAE 2.33 vs 2.38, breach AUC 0.8814 vs
0.880. Qualifiers that keep it honest: the delay and breach margins are
thin, GBM keeps the better worst-case delay tail, and all of it holds in
the practice world only.

**H2 — the timing hypothesis** *(formed after the first evaluation; tested
in 3c).* The rules engine's dominant error is charging every booking a
disruption's full delay estimate without asking whether the disruption will
still be standing when the vessel actually arrives — so adding that one
question should remove a large share of its false alarms at a small cost in
catches.
**Verdict: supported** — false alarms 484 → 308, catches 229 → 218 of 266,
accuracy 65.7% → 76.0%, on the identical dataset and split, verified by
re-running the same measurement after the fix.

**H3 — the witnessing bet** *(stated before the live runs; tested in 4a and
4d).* Sources built to published API shapes and covered by stub tests will
mostly answer on first real contact — but stubs are structurally blind to
one class of fault (servers rejecting request wording, real-world data
quirks like a dry model cell, rotted URLs), so a live run should surface
exactly that class and nothing else.
**Verdict: supported, almost to the letter** — 47 of 60 answered, and every
fault found was of the stub-invisible kind: three parameter rejections, one
dry-cell false alarm, one false caption, two dead links.

**And one deliberate non-hypothesis.** Nothing here claims anything about
real-world accuracy, because nothing could test it — that line stays
uncrossed until a real TMS provides real outcomes, and every number in this
file keeps saying so.

## 3. What we built

### 3a. The source layer: 42 → 60 (PR #47)

**Why:** breadth is the product's first differentiator — "one terminal for
everything that moves a lane." Breadth is only safe because no source is
load-bearing: each is its own small function inside a shared time budget,
reporting its own failure, read concurrently with the rest.

**What was added (+18):**

- **+10 RSS feeds** on corridor doorsteps: Rijnmond (Rotterdam's own
  broadcaster), Hamburger Abendblatt, ORF, Egypt Independent (Suez), News24
  and Daily Maverick (two readers on the Cape of Good Hope corridor, which
  previously had none), plus four trade-press feeds — The Loadstar, Hellenic
  Shipping News, Container News, and one safety-press feed.
- **+3 Rhine gauges** (Köln, Mainz, Maxau). The landing page keeps its three
  reference gauges (`config.LANDING_GAUGES`); the monitor reads all six, both
  resolved against one list so the two callers can never band a station apart.
- **+5 structured instruments:** Open-Meteo Flood (GloFAS modelled river
  discharge — a second, independent read on the Rhine, where *low* is the
  risk), DWD official weather warnings (a JSONP feed, unwrapped by bracket),
  EMSC seismic (a second reader beside USGS, same bands by design), GDACS
  disaster alerts (Red→high, Orange→medium, Green never an event), and NOAA
  NHC hurricanes as an honest *context* source that can never move a booking.

**How to run it:**

    python -m src.signals         # the 13 instruments alone
    python -m src.risk_monitor    # everything: news, gauges, instruments

### 3b. The ML layer: `ml/` (PR #47)

**Why:** the no-ground-truth problem above. The fix is a **synthetic TMS
world** with *latent* variables the desk never observes — true episode
severity, true duration, per-carrier reliability — and noisy proxies it does
(banded severities, published delay estimates, instrument readings). Realized
outcomes come from a structural model with irreducible noise, so labels come
from **realized cost, never from any policy**, and a model scoring
near-perfectly is treated as a bug by test, because in this world it would
have to be cheating.

**What it contains:** `ml/synth.py` (the world generator, stdlib-only,
byte-reproducible per seed: ~18 months of weekly departures over the real
route catalogue), `ml/features.py` (one authoritative feature list behind a
mechanical leakage fence), `ml/models.py` (stdlib baselines, **the shipped
rules engine itself** — imported, not copied — scikit-learn, TabPFN),
`ml/evaluate.py` (a time-based split with no episode straddling the boundary,
three tasks, reports with an honesty preamble).

**The three tasks, each tied to the Worker it would power:** *delay*
(regression — how late does this booking actually run; Risk/Milestones),
*action* (reroute / hold / no-action; Routing, as a consistency prior beside
the LLM, never instead of it), *breach* (probability the deadline breaks; the
approval queue's sort order).

**The guard rails**, all held by `tests/test_the_models_stay_honest.py`:
nothing in `src/` imports `ml/`; the root requirements and the Vercel bundle
carry no ML dependency (the demo is byte-for-byte unaffected); features are
blind to outcomes; the split cannot leak; and **synthetic-world numbers stay
in `ml/reports/` — they must never reach the pages, the README pitch, or a
demo script.**

**How to run it:**

    python -m ml.synth --bookings 6000 --seed 7    # generate the world
    pip install -r ml/requirements.txt             # numpy + scikit-learn
    python -m ml.evaluate                          # score everything
    python -m ml.evaluate --rerender               # rewrite the .md report
                                                   #   from the existing .json
                                                   #   without re-running models

### 3c. The timing question (PR #48) — the harness's first payoff

**What the harness found:** the shipped rules engine took every published
delay estimate at face value and never asked whether the disruption would
still be standing when the vessel actually reached the chokepoint. On the
committed seed it acted on **484 bookings the world left alone**.

**The fix:** `timing_factor()` in `src/route_advisor.py` weighs an episode's
age and type against how far off this booking's passage is — full weight
inside the expected-duration-plus-backlog horizon, half weight in the
uncertain middle, nothing when the vessel arrives long after the dust should
have settled. The judgment is recorded as its own step in the reasoning trail.

**Two design decisions worth remembering:**

- The question is asked **only when the event record carries
  `days_into_episode` and `days_to_passage`**. The ML world's facts do; the
  demo's authored events deliberately do not — their delay estimates are
  already per-booking impact forecasts, so discounting them again would count
  the same timing twice. The screenplay's outcomes are untouched *by
  construction*, and a guard test asserts the demo trails never pretend the
  question was asked.
- The constants are round desk numbers, **deliberately not imported from
  `ml/synth.py`** — a policy tuned to the simulator's exact parameters would
  be learning the answer key.

**Measured effect** (same seed, same dataset, same split; only the policy
changed — synthetic world only):

| shipped rules engine | before | after |
|---|---|---|
| accuracy | 65.7% | **76.0%** |
| macro-F1 | 0.507 | **0.579** |
| false alarms | 484 | **308** |
| real disruptions caught | 229 / 266 | 218 / 266 |

**Why it matters:** this is the first improvement in the project's history
that was *found by measurement, fixed in the product, and verified by
re-running the same measurement* — instead of asserted.

## 4. What we ran, and what running it found

Everything up to here was built in a sandbox that blocks every third-party
host, so it was stub-tested but **unwitnessed**. The rest of the day was
witnessing — running the real thing on the owner's Windows laptop — and every
run earned its keep by finding something no stub could.

### 4a. First real read of the instruments (`py -m src.signals`)

**Result: 10 of 13 answered on first contact.** Four faults surfaced, all
fixed the same day (PR #50):

1. **A false alarm — the worst kind of bug this project can have.** The
   GloFAS flood model answered **0 m³/s** for the Rhine: the grid cell
   nearest the Kaub coordinate sits *beside* the channel, and a dry cell
   reads as zero. The board turned that into a high-severity "critically
   low" event — an invented alarm. Fix: a plausibility floor
   (`DISCHARGE_MIN_PLAUSIBLE_M3S`) — anything below it is *no reading*,
   never a crisis, and the detail line says why. A guard test keeps it so.
2. **EMSC: HTTP 400.** The request used parameter shortcuts the US seismic
   service tolerates and the European one rejects. Now spec-literal.
3. **US NWS: HTTP 400** — an *original-eight* source whose request shape had
   simply never been witnessed. Now the minimal form the API's own docs use,
   with filtering moved into code where nothing can be rejected.
4. **GDACS: HTTP 400** from its JSON api. The source now reads the RSS feed
   GDACS has published since 2005 — on the retry it answered with **528 real
   alerts**, 516 of them Green and none inflated into events.

**Why witnessing matters:** a stub proves your code handles the *documented*
shape; only the real service proves your request survives contact with it —
and only the real world puts a dry grid cell where you pointed.

### 4b. Enabling TabPFN — four obstacles, each now written down

The enablement, on the owner's laptop, hit four walls in sequence. Each
lesson is recorded in `ml/README.md` and the adapter's own error message so
nobody pays for it twice:

1. **A plain `pip install tabpfn` ships the newer 2.5/3 weights, which are
   gated**: the first fit demands a Prior Labs account login — and that
   login's browser flow crashes outright on Windows (`WinError 10038`).
2. **The fix is a version pin:** `pip install "tabpfn>=2.0,<2.1"` ships the
   **TabPFN-v2 weights** — openly licensed (Apache-2.0 plus attribution), no
   account, no login. Also the license-safest choice for benchmarking.
3. **Python 3.14 was too new:** the pinned package wants an older
   scikit-learn with no prebuilt wheel there, so pip tried to *compile* it
   and died looking for a C compiler. Fix: Python 3.12 side by side
   (`py -3.12` on Windows).
4. **TabPFN refuses CPU runs over 1,000 training rows** unless
   `TABPFN_ALLOW_CPU_LARGE_DATASET=1` is set — a speed guard, not a fault.
   The run then takes a long while on a laptop; that is expected.

### 4c. The TabPFN verdict (witnessed on the owner's laptop, v2 weights, CPU)

**TabPFN won all three tasks, with zero tuning, in a single fit** —
synthetic-world numbers, recorded in `ml/reports/`:

| task | GBM (best classical) | **TabPFN v2** |
|---|---|---|
| Action (reroute/hold/nothing) | 88.1% acc / 0.608 macro-F1 | **89.5% / 0.666** |
| Delay (days late) | 2.38 MAE / **4.85 P90** | **2.33 MAE** / 5.34 P90 |
| Breach probability | 0.880 AUC / 0.1287 Brier | **0.8814 / 0.1284** |

**How to read it honestly:** the action edge concentrates on the rare classes
(hold recall 51% vs GBM's 33%) — the decisions that are the whole point. GBM
keeps the tighter delay *tail* (better worst-case promise; TabPFN better
typical guess). And one number accuracy hides: of the 266 bookings that
genuinely needed action, the rules engine moved on 218 while TabPFN — the
accuracy winner — moved on 133. A model can be right more often by acting
rarely; a policy can miss less by acting constantly. Which error costs more
is a desk decision, not a modelling one.

**None of this transfers to real freight.** It says TabPFN learns this
controlled world better than GBM does. The day real TMS history exists, the
same harness runs unchanged and produces numbers that mean something
operationally.

**A bug the verdict itself exposed (PR #52):** the report's prose still
called GBM "the best model" — hard-coded when GBM led — directly under
tables showing TabPFN winning. The same disease as a hard-coded "live" chip,
caught in this repo for the second time. Every "best model" claim is now
*computed* and **names the winner beside the number**, guard-tested so a
future overtake can never desync the prose again; and `--rerender` rebuilds
the report from the stored results so a wording fix never costs another
multi-hour CPU run.

### 4d. First real read of the news family (`py -m src.risk_monitor`)

The last unwitnessed claim in the project — "the risk detection is real."

**Result: 28 of 30 feeds answered with 583 real items**; the prefilter
surfaced 40 chokepoint mentions; **non-English sources produced real
events** — including NDR Hamburg carrying an actual Hamburg transport
closure ("A1 … bis Montag gesperrt"), which is the demo's own story
happening unscripted. All six gauges read live against a Rhine that
genuinely was low that day (five real low-water events). With no AI key on
the machine, classification ran the keyword path and **every such event said
so on screen** ("KEYWORD MATCH ONLY — no LLM was used") — including the junk
matches ("Kenya tear gas → SUEZ") that exist precisely to show what the
model's filtering is for.

Three faults, fixed the same day (PR #53):

1. **A false caption:** Maxau at 370 cm (warn band, threshold 380) was
   captioned "at or below the **320** cm restriction threshold" — quoting a
   band it had not crossed. Right severity, false sentence. The event now
   quotes the threshold the band walk actually stopped at, guard-tested
   across all three bands.
2. **Al Jazeera Arabic's feed URL had rotted (404).** BBC (العربية) replaces
   it — and the corridor kept two other Arabic readers throughout, which is
   exactly what the two-reader redundancy exists for. (A note for the
   record: the first attempt named the replacement "BBC Arabic", and the
   pages' own no-language-name test **rejected it**, forcing the same
   native-script convention the other Arabic services use. The guards guard
   their own authors.)
3. **SAFETY4SEA served HTML where its feed should be.** FreightWaves
   replaces it. Both replacements are unwitnessed until the next run, and
   say so in `DATA-SOURCES.md`.

## 5. How all of this helps

**The demo got its credibility.** The central honest claim — live, multilingual,
wide reading — is no longer an architecture diagram; it has been watched
happening: real German headlines producing events about Hamburg, real gauges
banding a genuinely low Rhine, 52 of 60 sources answering, and the failures
degrading exactly as designed, each with a readable reason.

**The product got measurably better.** The timing question removed a third
of the rules engine's false alarms — and more important than the one win,
the *instrument* now exists: any future change to the decision policy can be
measured against ground truth instead of argued about.

**The TabPFN question is answered.** Usable — yes, on the openly licensed v2
weights, free of login and license traps, and the strongest backend in the
harness. The day there is real booking history, the shelf is already
stocked, the pitfalls are pre-cleared, and the harness runs unchanged.

**The honesty system proved itself.** Twice today the repo's own guards
caught its own author — a language name in page copy, prose drifting from
its tables — and twice the fix made the class of error structurally
impossible rather than patching the instance. That is the difference between
a project that *is* honest and one that merely was at the last review.
