# The ML layer — prepared, not wired

This folder is the machine-learning layer that could one day power SQRlane's
agents. It is **prepared, not wired**: nothing in `src/` imports it, the demo
runs exactly as before without it, and the Vercel deployment does not ship it.
A test suite (`tests/test_the_models_stay_honest.py`) fails the build if any
of that quietly changes.

## Why it exists, and why it is built this odd way

The obvious next step for a decision product is "train a model on the
decisions". That step had a blocker worth writing down: **this repo had no
ground truth.** The only decisions in it come from the shipped rules engine
(or the LLM) — so a model trained on them would just relearn an if-statement,
and an "accuracy" number from that exercise would be exactly the invented
metric this project refuses to produce.

The fix is a synthetic **world**, not a synthetic dataset of decisions
(`ml/synth.py`). It simulates about eighteen months of weekly departures over
the demo's real route catalogue. Disruptions arrive at each chokepoint as
episodes with **latent** true severities and durations the learners never see;
what they see instead is what a desk sees: a severity band that is sometimes
misread, a published delay estimate, a headline count, an instrument reading
where one exists (a Rhine gauge, port gusts, wave height). Then, for every
booking, the generator plays out what each of the three possible actions —
do nothing, hold, reroute to the best alternate — would **really** have cost,
using the latent state plus noise, priced with the product's own cost
arithmetic (`src.route_advisor.cost_of`, imported rather than copied). The
label is the action that really was cheapest.

So labels come from **realized outcomes**, not from any policy — which means
the shipped rules engine can be scored against this world like any other
model, instead of being the unbeatable answer key.

**What that buys, and what it does not:** models trained here have learned the
simulated world. The numbers in `ml/reports/` compare model families against
each other and against the shipped rules engine inside a world we control.
They say **nothing** about accuracy on real freight, and they must never
appear on the product pages, in the README's pitch, or in demo narration.

## The three models and what each would power

| Model | Task | Where it would plug in |
|---|---|---|
| **Delay** | regression: how many days late does this booking actually run | the Risk and Milestones Workers — a delay number you could put in a status line or a customer draft |
| **Action** | classification: reroute / hold / no-action | the Routing Worker — as a consistency prior beside the LLM: when the model and the LLM disagree, that disagreement is itself a signal worth surfacing |
| **Breach** | probability the deadline breaks | the approval gate — sorting the queue by urgency, so a person works the riskiest booking first |

None of them is plugged in anywhere today. That is the "not wired" half of the
headline.

## How to run it

```bash
# 1. generate the world (standard library only - no installs needed)
python -m ml.synth --bookings 6000 --seed 7

# 2. install the learners' dependencies (numpy + scikit-learn)
pip install -r ml/requirements.txt

# 3. train and score everything that can run; writes ml/reports/
python -m ml.evaluate
```

The generator is deterministic: the same seed produces byte-identical output,
so the exact dataset behind any report can be regenerated by anyone. The full
book (`ml/data/tms_synthetic_bookings.json`, ~13 MB) is gitignored for that
reason; a 50-record sample is committed so the schema is reviewable.

`python -m ml.evaluate` splits **by time**: the first ~70% of the timeline
trains, the rest tests, and no disruption episode is allowed to straddle the
boundary (bookings tangled across it are dropped, and the harness asserts the
two episode sets are disjoint). Backends whose dependencies are missing are
skipped with a printed reason, not crashed into.

## What the current numbers look like, and the calibration behind them

The committed reports (`ml/reports/evaluation.md` / `.json`) were produced
from 6 000 bookings, seed 7; the report records the exact Python and
scikit-learn versions it was scored on (the dataset is byte-reproducible
from its seed, but sklearn numbers can drift across releases). Headlines:
the gradient-boosting model decides reroute/hold/no-action at about 88%
against an 84% "always do nothing" floor (macro-F1 0.62 vs 0.30 — the
learner's edge is on the rare classes, which are the ones that matter); the
shipped rules engine lands at about 76% — and that number carries this
harness's first measured product improvement: the first evaluation scored the
rules at 66%, acting on 484 bookings the world left alone, because they took
every published estimate at face value and never asked whether the episode
would still be alive when the vessel got there. Teaching the advisor that one
timing question (`timing_factor` in `src/route_advisor.py`, asked only when
the record carries the facts to answer it) removed 176 of those false alarms
at the cost of 11 real catches (recall 229→218 of 266) and lifted the rules
past the logistic learner on macro-F1 — a non-ML change, found by the
harness, verified by re-running it; the delay model is off by
about 2.4 days where guessing the average is off by 7.2; the breach model
ranks a breaching booking above a safe one 88% of the time.

The noise was **calibrated on purpose** so the task is learnable but never
saturated — an early version let the best model tie the majority baseline
(world too noisy), a later one nearly saturated it (world too quiet). The
final knobs live in one place (`NOISE` and `TYPE_PARAMS` in `ml/synth.py`):
severity bands misread 15% of the time, a lognormal sigma of 0.35 on every
episode's realized bite (drawn once per booking and shared across the
counterfactual arms, so labels never flip on noise nobody could predict),
sigma 1.0 of ordinary schedule slip, episodes that start after the decision
scaled to 0.45 of their bite in every arm alike (a later disruption gets a
later decision of its own — nobody is scored on clairvoyance), and a EUR 500
indifference band under which the label prefers the calmer action. A test asserts the anti-saturation property: if any model
ever hits 100% here, the world is broken, not the model brilliant.

## TabPFN — present, adapted, unwitnessed

[TabPFN](https://github.com/PriorLabs/TabPFN) is a tabular foundation model:
sklearn-style fit/predict, a single forward pass instead of training, and its
published strength is small tables — which is what a forwarder's booking
history is. It has a slot in the registry via `ml/tabpfn_adapter.py`.

It has **never run here**. The package needs PyTorch and downloads its
weights from Hugging Face on first fit; this build sandbox blocks that host,
so the adapter is built to TabPFN's published interface and degrades to a
readable "here is how to enable it" message — the same posture the repo takes
with its eight unwitnessed structured sources. To enable it on a real
machine: `pip install -r ml/requirements.txt`, then
`pip install "tabpfn>=2.0,<2.1"` (pulls torch), then run once with internet
so the weights cache. The version pin was learned by witnessing: a plain
`pip install tabpfn` ships the newer gated 2.5/3 weights, whose mandatory
Prior Labs account login crashes outright on Windows (`WinError 10038`) —
the 2.0.x package ships the openly licensed v2 weights and needs no login.
Two more facts from the same witnessing session: use **Python 3.12 or
older** for this backend (`py -3.12` on Windows — the pinned package wants
an older scikit-learn that has no prebuilt wheel on newer Pythons, so pip
tries to compile it and dies looking for a C compiler), and on CPU with
more than 1 000 training rows TabPFN refuses to start unless
`TABPFN_ALLOW_CPU_LARGE_DATASET=1` is set — a speed guard, not a fault,
and a CPU run over this dataset takes a long while.

Two caveats travel with it, and they are in the adapter's error message so
they cannot be missed:

* **License.** The TabPFN code and v2 weights are Prior-Labs-License
  (Apache-2.0 plus required "Built with PriorLabs-TabPFN" attribution when
  distributed). The newer 2.5/3 weights are **non-commercial**: benchmarking
  internally is fine, shipping them is a license decision to make on purpose.
* **Privacy.** `tabpfn-client`, the hosted-API variant that needs no torch,
  **sends the table to Prior Labs' servers**. Synthetic bookings are harmless;
  a real forwarder's booking history is customer data, and pointing the
  client at it without a data-processing agreement and sign-off would be a
  privacy failure. The adapter deliberately does not wire it.

## What remains unwitnessed or unknowable from here

* **TabPFN itself** — adapter built to the published interface, never
  executed in this sandbox (see above).
* **Any claim about real-world accuracy.** The whole layer runs on a world a
  generator invented. Whether these models help on real freight needs real
  TMS history — bookings, disruptions and realized outcomes from a live
  forwarder — and that data sits on the far side of the same
  integration/trust wall as the live TMS connection itself. Until it exists,
  every number in `ml/reports/` stays a statement about the simulation, and
  stays out of the product's pages.
